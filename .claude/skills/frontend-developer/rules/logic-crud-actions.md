# CRUD Actions and Confirmation

This rule dictates how Page Components construct their primary Action columns within the DataTable and how mutations (edits and deletes) are guarded to ensure a consistent UX.

## Scope

This rule only applies to **model-management pages**: a page built around a `<DataTable />` that lists records of a model (typically the page generated by `generate_ui_model`/`generate_ui_models`) and lets the user view/edit/delete rows. A page with a different purpose — a contact form, a checkout step, a public landing page — has no list to manage and is **not required** to render the three `<ActionButton />` actions or follow the view-only/confirmation-modal mechanics described below.

That said, the form/request itself still must follow the rest of the **Logic** category (`logic-form-payloads`, `logic-state-machine-controllers`, `logic-map-methods`): the FSM controller-hook pattern, the `REPLACE_`/`UPDATE_` payload conventions, and the fetch/transform helpers are conventions for *any* form or API call in the project, not only for model-management ones. Only the list+actions UX described in this file is CRUD-specific.

## The Rule

1. **DataTable Action Columns**: The `Actions` column of the table _must_ always render three inline `<ActionButton />` components by default:
   - **View**: Mode `neutral`, icon `FiEye`. Clicking opens the modal with the form in a disabled (`viewOnly = true`) state.
   - **Edit**: Mode `secondary`, icon `FiEdit2`. Clicking opens the modal with the form populated for editing.
   - **Delete**: Mode `error`, icon `FiTrash2`. Clicking triggers the Confirmation Modal logic.
2. **Action Icons Sizing**: DataTable Action Buttons must be scaled down uniformly using inline styles (`width: "2rem", height: "2rem", fontSize: "1rem"`) to preserve tight table rows layout without inflating the `ActionButton` globally.
3. **Form Disable Mode (View Mode)**: Page components must respect an `isViewMode` state. When active, all fields injected into the `<Form />` must be injected with `disabled: true`. The `<Modal />` encapsulating the form should rename its title contextually (e.g. "View Item") and omit the confirmation/save logic, leaving only a "Close" button.
4. **Mutations Guarding**: Every destructive mutation (`REMOVE_`) or state modification (`REPLACE_`/`ADD_`) must be guarded by a secondary, generic confirmation `<Modal />`. Do not push mutations directly to the API without first popping up a confirmation dialog for the user (e.g., "Are you sure you want to save these changes?").

## Implementation Template

```jsx
// 1. Defining the Actions in DataTable Column configuration
<DataTable
  columns={[
    ...itemTableConfig,
    {
      key: "actions",
      label: "Actions",
      width: "120px",
      renderCell: (_, item) => (
        <div style={{ display: "flex", gap: "0.25rem" }}>
          <ActionButton
            icon={<FiEye />}
            type="neutral"
            onClick={() => handleRowEdit(item, true)} // viewOnly flag
            style={{ width: "2rem", height: "2rem", fontSize: "1rem" }}
          />
          <ActionButton
            icon={<FiEdit2 />}
            type="secondary"
            onClick={() => handleRowEdit(item, false)}
            style={{ width: "2rem", height: "2rem", fontSize: "1rem" }}
          />
          <ActionButton
            icon={<FiTrash2 />}
            type="error"
            onClick={() => handleRowDelete(item)}
            style={{ width: "2rem", height: "2rem", fontSize: "1rem" }}
          />
        </div>
      ),
    },
  ]}
  data={tableData}
/>;

// 2. Applying viewOnly mode explicitly across config dynamically
const handleRowEdit = (item, viewOnly = false) => {
  setIsViewMode(viewOnly);
  const populatedFields = formFields.map((field) => {
    const val = item[field.name || field.id];
    // Map existing structure and inject `disabled`
    return {
      ...field,
      value: val !== undefined && val !== null ? val : "",
      disabled: viewOnly,
    };
  });
  setFormFields(populatedFields);
  setIsModalOpen(true);
};
```
